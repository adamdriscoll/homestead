# Contributing

Use the .NET 10 SDK, Node.js 24, and Hugo 0.152.2 (standard or extended).
Hugo is a test/export consumer dependency; it is not part of the app container.
`global.json` selects an installed .NET 10
feature band and excludes preview SDKs. NuGet and frontend dependencies use exact
versions; npm's lockfile is committed. CSS is generated by the application build.

## VS Code

Open the repository root in VS Code with the recommended C# extension and
PowerShell 7 available on PATH. **Ctrl+Shift+B** runs **Homestead: build**, including
the CSS build. In Run and Debug, choose **Homestead: .NET** and press **F5** to build
and debug at `http://localhost:5080`. Its data is kept separately in `data/vscode`.
The first launch generates a random setup token in the ignored
`.homestead-local/vscode/.env`; open that file locally and use its value at
`http://localhost:5080/setup`. After setup, clear the token value in that file.

With Docker Desktop's Linux engine running, choose
**Homestead: persistent container (build and launch)**. This builds current source
and starts the persistent instance at `https://127.0.0.1:5444`. Subsequent launches
use the local runner's Upgrade operation: snapshot the data and pin the old image
before replacing it. Saved port/configuration overrides are retained.

If Docker has removed the saved image, the launch instead uses Recover: archive
the existing data and start current source on a new volume restored from that
archive. The original volume remains untouched. The recovery archive records the
missing image ID but cannot provide paired image/data rollback without that image.
Normal upgrades resume after recovery. Avoid pruning local backup image tags if
you need rollback; Docker images are separate from the data archives.

The terminal follows container logs; stopping the launch leaves the instance running. Use
**Tasks: Run Task → Homestead: stop persistent container** to stop it while
preserving data. The container target launches the production image and tails
logs; use the .NET target for C# breakpoint debugging.

For first-run container setup, retrieve its token in your own terminal:

```powershell
pwsh -NoProfile -File .agents/skills/homestead-local/scripts/homestead-local.ps1 -Environment Persistent -Action Token
```

After creating the administrator, run the same command with
`-Action CompleteSetup` to clear the token and recreate the app. The local Caddy
CA may need trusting in your browser; use `-Action TrustCertificate` on Windows
when you want to trust this instance's CA. Local state, tokens, and backups live
under ignored `.homestead-local`; preserve it to retain image/volume selections.
For backup and rollback operations, follow the repository's
[local Docker skill](../.agents/skills/homestead-local/SKILL.md).

## Quality checks

`ScheduledPublicationTests` uses migrated SQLite, a fake clock, and activation
faults to cover all seven types, private frozen copies and photos, stale versions,
replacement/cancellation, manual publication actions, DST ambiguity and skipped
times, overdue restart/restore, retry timing, Hugo draft bundles, authenticated and
antiforgery forms, and updates/listings/previews in all five built-in themes.
Browser schedule tests cover ordinary and enhanced forms, autosave before
scheduling, replace/cancel, mobile/light/dark layouts, and real worker activation
without exposing later edits. The scheduled-posts migration creates a private
`PostSchedules` table without rebuilding `Posts` or changing its publication
trigger. No environment configuration or external service is added.

`AutomatedBackupTests` covers persisted schedules, concurrent checks, retry timing,
private protected credentials, authenticated/antiforgery settings forms, disabled
backups, pre-build failure with pending desired state, archive cleanup, and full
restore with the saved key ring. Browser backup tests exercise the Backup tab,
credential retention, safe upload errors, disabling, mobile layout, light/dark
appearance, and ordinary forms without JavaScript. Automated tests use isolated
data and fake upload destinations; no developer bucket receives test backups.
`S3BackupUploaderTests` exercises signed single-object and multipart uploads over
a disposable loopback server, checking complete payloads and path-style requests.
The automated-backups migration creates a separate private configuration/status
table. It does not alter posts or public theme models, and existing installations
start with backups disabled.

### Browser tests

`tests/Homestead.Playwright` is a separate Node.js 24 project using Playwright Test.
It runs Chromium with desktop and mobile viewports against the production Docker
image through Caddy HTTPS. Install its dependencies and browser once, then run it
from the repository root with Docker's Linux engine and Compose available:

```sh
npm ci --prefix tests/Homestead.Playwright
cd tests/Homestead.Playwright
npx playwright install chromium
cd ../..
npm test --prefix tests/Homestead.Playwright
```

On Linux, use `npx playwright install --with-deps chromium` to install the browser's
system dependencies too. By default, each test run builds the current checkout.
To reuse an image you have already built, set `HOMESTEAD_PLAYWRIGHT_IMAGE` to its
local tag or image ID; the suite resolves it to an immutable ID before testing.
Playwright tests are temporarily excluded from CI. Continue adding browser coverage
and running the suite locally for relevant changes; CI still runs the .NET checks
and Docker smoke test.

Every test creates its own uniquely named Compose project, fresh data and TLS
volumes, Docker-allocated network, random setup secret, and dynamically assigned
loopback HTTPS port. Teardown removes only that test project's containers, network,
and disposable volumes, including after a failed test or startup. It never connects
to the local runner's sandbox or persistent installation. An abruptly killed test
runner may leave a project named `homestead-playwright-<random ID>`; inspect
`docker compose ls -a` and remove only that project's resources if cleanup is needed.
TLS verification is skipped only for these test instances' internal Caddy CAs.

The suite exercises browser setup/login/logout, autosave and stale-tab conflicts,
private preview, publication/update/unpublish/delete, Markdown formatting and inline
image uploads, gallery batch uploads/captions/order, all seven post types, and public
navigation and article forms without JavaScript. Mobile emulation does not replace
the physical-phone acceptance checks in release readiness.

Use `npm run test:headed --prefix tests/Homestead.Playwright` for a visible browser,
`npm run test:ui --prefix tests/Homestead.Playwright` for Playwright's test UI, or
`npm run test:desktop --prefix tests/Homestead.Playwright` for desktop only.
Screenshots, videos, traces, and container logs are retained on failure under
`output/playwright`; the HTML report is available with
`npm run report --prefix tests/Homestead.Playwright`. These tests supplement the
.NET integration tests and deployment/portability smoke rather than replacing them.

### Application checks

`FitnessTests` covers GPX 1.0/1.1 and Garmin sensor extensions, segment boundaries,
missing timestamps/sensors, malformed XML/DTD/coordinate/measurement limits,
authenticated and antiforgery-protected imports/downloads, stale draft conflicts,
all built-in theme listings/details/previews, photo rendering, private replacements
and removals, failed builds/retry, lifecycle, static exports, real Hugo builds, and
backup restoration of original GPX bytes and committed snapshots. Browser fitness
tests use isolated Docker data and fixture tracks, checking autosave before imports,
ordinary forms without JavaScript, mobile/light/dark rendering, and each theme.
The fitness migration expands post/newsletter type constraints, adds private
`FitnessActivities` and `EnableFitness`, and restores the publication trigger in a
separate migration after SQLite's Posts rebuild. Existing newsletter preferences
keep their selected types. No new environment configuration or runtime service is
needed. The fitness-display-units migration adds a metric-default preference and
an enum constraint to SiteSettings without changing stored GPX measurements.
Fitness tests cover both unit systems in every built-in theme, settings validation,
failed rebuilds and active static exports, restart, RSS, Hugo, and backup restore.
Leaflet browser checks cover segmented route lines, start-marker keyboard activation,
private map consent, mocked tile loading/failures, responsive light/dark maps in all
themes, icon-only toolbar placement and keyboard route fitting after zoom,
tab selection/keyboard navigation, map resizing after tab changes, conditional
heart-rate tabs, and
JavaScript-free statistics/charts with map guidance. They never request production tiles.
Route maps reuse the existing Leaflet bundle and need no additional migration.

`NewsletterTests` uses real migrated SQLite and a fake Brevo sender/clock. It covers
confirmation and authenticated settings forms, antiforgery, protected API keys,
cadence/type preferences, snapshot privacy, failed activation, delivery retry and
restart, removal before a digest, every built-in theme, export privacy, and backup
restore with working management links. The newsletter migration adds private
settings/subscriber/activation/delivery tables and a disabled-by-default public
navigation flag; it does not rebuild `Posts` or change published snapshots.
Browser newsletter tests use fake credentials and never submit signup emails to
Brevo; they cover settings, all theme forms, mobile/light/dark layouts, and ordinary
forms without JavaScript. Real-provider acceptance remains a manual check with
the administrator's own Brevo account and verified sender.

```sh
dotnet restore
dotnet build
dotnet test --no-build
dotnet format --verify-no-changes --no-restore
dotnet tool restore
dotnet ef migrations has-pending-model-changes --project src/Homestead --no-build
```

Integration tests use real migrated SQLite files in isolated temporary directories
and ASP.NET Core's test host. They cover secure setup, single-account races,
authentication, CSRF, private storage, settings, cookies, and restart behavior.
Article tests also cover the complete publication lifecycle, autosave conflicts,
upload signatures/decoding, HTML safety, isolated previews, concurrent publication,
failed generation/retry, missing media, active-site recovery, and public requests
that are forbidden from querying SQLite.
Public-experience tests cover microblog text/photo combinations, mixed chronological
feeds, tag-slug collisions, XML feeds, complete social metadata, branding replacement
and failure/retry, safe profile links, and upgrades from Phase 2. The production
Compose smoke also checks notes, static listings/About/tags, discovery, and restart.
`FaviconTests` covers the bundled default, custom upload/replacement/removal across
all five themes, authenticated preview URLs, failed activation and retry, static
and Hugo export assets, and backup restore. The public-favicon migration adds a
nullable branding reference; existing sites use the default after rebuilding.
Domain tests exercise database constraints rather than an in-memory provider.
Five-type tests cover every publication lifecycle, structured draft isolation,
review validation, step/photo ordering, captions and alt text, foreign-media/step
rejection, safe Markdown, conflict detection, batch uploads, and failed build retry.
The Compose smoke publishes all seven types and checks locations and gallery batch uploads.
The CI workflow also builds and tests the Linux container with Caddy.
Portability tests build the exported Hugo project with the real CLI and restore
checksum-verified backups. Reliability tests inject activation and database
failures, including upload cleanup and post-activation reconciliation. The Docker
smoke serves the static export with Homestead stopped and restores a backup into
a fresh volume. `PortabilityTests` invokes the real Hugo CLI with `--panicOnWarning`;
set `HOMESTEAD_HUGO` to its binary path if it is not on PATH. Set
`HOMESTEAD_FIXTURE_OUTPUT` to a directory to retain static/Hugo fixture ZIPs;
CI uploads them as `portability-fixtures` artifacts.

`PublishingTests`, `FiveTypeTests`, and `ReliabilityTests` cover render/staging
failure, activation failure, interrupted-build recovery, post-activation database
failure, failed unpublish, concurrent publication, and upload/backup races.
Corrupt-generation tests verify readiness failure and explicit rebuild recovery.
The real disk-exhaustion check and other infrastructure/device acceptance remain
tracked in [release readiness](https://github.com/PoshTools/homestead/issues/22).

When the domain model changes, add a migration:

```sh
dotnet ef migrations add ChangeName --project src/Homestead --output-dir Data/Migrations
```

The initial migration creates a SQLite trigger to lock the first publication slug
and timestamp. Preserve it explicitly in any future migration that rebuilds the
`Posts` table; [SQLite migrations have provider-specific limitations](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/limitations).
The location/check-in upgrade restores it in a separate migration, after EF's
deferred SQLite table rebuilds have completed. Adding SQL to the same migration
can recreate the trigger before the rebuild and then silently drop it again.
All persisted timestamps use UTC; nullable ratings allow incomplete drafts, and
nonnull ratings are constrained to integers 1–5.
Location coordinates are nullable, must be supplied together, and are constrained
to latitude -90–90 and longitude -180–180. `LocationTests` and the existing
lifecycle/portability fixtures cover locations and check-ins, draft isolation,
validation, stable URLs, and legacy snapshots. Browser tests cover check-in
autosave, private preview, and public navigation without JavaScript.
`LocationMapTests` covers the optional public map, snapshot privacy, all post
types, removals, failed activation, and restart. Portability tests build the Hugo
map and retain it in static exports and restored backups. Browser tests check
Leaflet markers, shared-place popups, safe text, tile failures, and navigation
without JavaScript on desktop and mobile viewports. Automated tests mock tile
requests rather than repeatedly downloading OpenStreetMap tiles.

`GuideTests` covers tools and materials with optional HTTP(S) links, nullable step
durations, Humanizer display, legacy snapshot defaults, and draft isolation.
Guide steps use the shared Markdown toolbar with inline photo upload, paste, and
drop. Each step has a title and an independent collapsible header. Collapse state
is retained by step ID in browser session storage across reloads and reordering;
native collapse also works without JavaScript. Titles are plain text, at most 300
characters, and may be empty for existing or unfinished steps. The step-title
migration adds nullable text without altering step IDs or photo assignments.
Durations use a single time picker for elapsed hours, minutes, and seconds. Leave
it blank to omit the time. The input model uses a nullable `TimeSpan`; stored
duration seconds and published snapshots stay compatible without a migration.
Humanizer uses hours as the largest display unit. Older durations exceeding the
picker's range are retained on ordinary saves, with a picker to replace them
explicitly (00:00:00 clears an older duration).
Materials have a separate optional text
quantity field, such as “10 boxes” or “5 switches”. Every included supply needs
a name before publication.
The guide-supplies migration retains existing steps and adds a private supply
table and nullable duration column. Hugo exports retain ordered supplies and
duration seconds in front matter and readable lists and times in Markdown.
The material-quantities migration adds nullable text; existing material names
and links remain intact, and existing quantities stay empty until edited.
Browser guide tests cover separate Tools and Materials tabs, keyboard navigation,
autosave, formatting, photos, reordering, and ordinary forms/public pages without
JavaScript.

`SocialSharingTests` covers opt-in sharing, independent selections, URL/title
encoding, published snapshot privacy, all built-in themes and post types, failed
activation/retry, static exports, and settings restart compatibility. Browser
sharing tests exercise Social settings, light/dark layouts, ordinary links without
JavaScript, and private previews across all built-in themes. The social-sharing
migration adds six disabled-by-default settings; it does not change post data.

`ThemeTests` covers Razor theme packages, rejection of unsupported layouts, typed
models for all seven types, template precedence, preview media URLs, source privacy,
compilation/render failures, and backup/Hugo portability. Razor's public language
compiler and Roslyn are exact NuGet dependencies shipped in the runtime image;
server installations do not need the .NET SDK. Theme authoring and the trust
boundary are documented in [themes](themes.md).

Choose work from [GitHub issues](https://github.com/PoshTools/homestead/issues),
and define scope and acceptance before implementing deferred proposals. See
[agent guidance](../AGENTS.md) for architecture and compatibility invariants.
There is one application project, no SPA, and no runtime Node dependency. The public
root contains compiled CSS, the plain editor script, and install-manifest/icons. Private originals, SQLite, backups, and keys
must never be registered with static-file middleware. Do not add public Identity
UI or registration scaffolding; administrator creation belongs solely to setup.
